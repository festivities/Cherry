   **Design (agent, decided unless marked open; the user asked for better ideas and approved the storage choice):**
   - **P1 Storage: SQLite (WAL, `modernc.org/sqlite`, pure Go, builds for linux/arm64) on local disk, replicated by Litestream to a private R2 bucket.** D1 keeps its current job (the asset manifest). Reasons: D1 from outside Workers goes through Cloudflare's REST API, which is meant for admin use, shares the account-wide limit of 1,200 requests per 5 minutes (excess calls get 429 for five minutes) and needs a proxy Worker for app traffic; a D1 database also runs one query at a time. Cherry touches its data on almost every game message, so an in-process database with µs reads and real transactions fits. Litestream settings: `sync-interval` of 30 s or more to stay inside R2's free tier (1,000,000 Class A operations a month); a restore drill into an empty directory before go-live; the backup bucket and its token are separate from `cherry-assets`.
     - **Connection setup (revised 2026-11-10):** one write connection (`SetMaxOpenConns(1)` on the write handle, transactions started as IMMEDIATE) so writers queue in Go and never see `SQLITE_BUSY`; a small separate read pool; `journal_mode=WAL`, `synchronous=NORMAL`, a `busy_timeout` of about 5 s (Litestream takes short locks), `foreign_keys=ON`. Check the driver's DSN parameters and Litestream's own guidance on checkpointing at spec time; neither was looked up for this note.
     - **Player media stays as files** (`diary-media\`, `profile-media\`, `room-media\`): Litestream does not cover them. Whether they are also copied to the private bucket is open (see "Still open").
   - **P2 Refactor, not rewrite: swap the persistence, keep the model (revised 2026-11-10).** Keep the protocol handlers (months of device-verified client knowledge) and keep `store`'s in-memory structs as the authority. What goes is the whole-file save.
     - **Save names what changed.** `store.SaveAccountsLocked()` becomes a save that takes the accounts it touched and writes, in ONE transaction, those accounts' rows, the ledger lines of the operation and any token rows. The 69 call sites change mechanically (delete the old function and the compiler lists them). The ledger thereby becomes atomic with the balance (today the append comes after the save and its failure is only logged).
     - **Safety net for missed accounts:** in test builds every save also checks that no account it was NOT given differs from its last written form. The existing 41,000 lines of tests then prove the conversion; keep "empty store path = memory only" so they run unchanged.
     - **Schema v1:** `accounts` keyed by an internal id, not the aid (an account has aid `"0"` until `create/avatar`, so several can share it), with the columns lookups need (aid unique when set, Discord id, guest-code hash, name) and the rest of `StoredAccount` as one JSON column; `tokens` (hash, account, created, last used); `ledger`; social as one row per friendship, post, comment, like and guestbook entry; one row per circle and per Treasure World record; `documents` (P3); `audit` (P4); the auth tables of CONTRACT §3. Loaded into memory at start, as today.
     - **Write volume:** one JSON column means a save rewrites that account's whole state (1001's is about 300 KB, a new player's a few KB). Measure WAL bytes per mutation in 8.3b. If Litestream volume or latency says so, split the column into a few parts (balances and daily counters, closet, room, mail, the rest) and write only the parts whose hash changed: no call-site change.
     - **Locks stay at first.** `AccountsMu` and `SocialMu` keep their meaning; the write under the lock shrinks from all data to one account. P9 decides what follows.
     - **Normalize later, only where it pays:** inventory or diary lists become real tables when a query needs them or memory says so, not before.
     - **Proof:** a round trip of the real lab stores (JSON → DB → memory → the `StoredFrom` dump equals the input; private, run locally) plus synthetic fixtures in the tests; golden dumps before and after each step, as Roadmap 4a did. Production starts empty (decision 5); the lab importer is `cmd/cherry-import`, lab only.
     - `ponytail:` ceiling to write in the code: all accounts live in RAM. Upgrade path when the load test or memory says so: load on demand, evict idle accounts, keep a slim always-loaded profile index (name, outfit) for friend lists and search.
   - **P3 Operator data as documents (revised 2026-11-10).** The `data/*.json` operator files become versioned documents in the DB: draft → validate with the existing `check*` validators → publish, with history, rollback and audit. The embedded defaults remain the seed; "ground truth stays in code" (Policies) is unchanged.

The `config\` directory keeps only switches (`streaming.json`, `itemconv.json`) and the lab's overrides.

Each document says whether it is hot or needs a restart; a document becomes hot only together with a test that its derived caches follow (shop catalog, gacha pools, calendar skin versions, menu).

     - **Listener:** its own port and its own `tls.Config` (TLS 1.2 ECDHE-GCM and 1.3 only, no static-RSA suites); no admin route on the game listener and no player route on this one; HSTS.
     - **Its own hostname too (revised 2026-11-10; needs the user's yes, "Still open"):** browsers do not separate cookies by port, and "same site" ignores the port, so on one hostname the admin session cookie would also be sent to the game HTTPS listener, and a flaw in any player-facing web page there (the odds and HELP pages render operator-editable content) would sit on the admin's site. With a second name (for example `admin.<domain>` beside the endpoint name) the `__Host-` cookie stays on the admin host only. Cost: one more DNS record and one more name on the certificate. Without it, keep the CSRF token and the `Origin` check as the only wall and never serve operator-editable HTML on the game listener.
